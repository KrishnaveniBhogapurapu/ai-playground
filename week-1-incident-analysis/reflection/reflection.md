# Week 1 reflection

Across zero-shot, one-shot, and few-shot prompting, the output structure became more explicit, but factual reliability did not consistently improve. The zero-shot response returned valid JSON and useful hypotheses but left assumptions empty. The one-shot response added assumptions and made rollback conditional on evidence. The few-shot response used contradicting evidence more actively, but it also claimed that errors began before deployment, credential checks had already occurred, and database latency preceded the provider report. Those details were not in INC-104, and the pre-deployment-error claim closely resembled one of the examples. Because I stored only one response for each prompt approach, I cannot declare one approach best from these samples.

Changing generation parameters changed hypothesis ordering, the number and grouping of hypotheses, fact coverage, recommended actions, wording, and sometimes JSON quality. There was no simple pattern showing that a lower Temperature or a particular Top-P was more correct. The Repeat Penalty 0.7 output became repetitive and incomplete, while both Repeat Penalty 2 outputs were invalid JSON and corrupted incident details. Frequency Penalty was not available in the LM Studio interface, so I recorded it as unsupported rather than estimating a result.

Greater consistency did not make the analysis more correct. The two Min-P 1 files were exactly identical, but both still used unsupported timing and failure-mode language. They showed repeatability, not proof. In the same way, valid JSON only showed that an output followed a parseable format; it did not verify the claims inside it.

The alert time, failure-rate increase, deployment completion, increased database latency, provider report, and previous credential incident were supplied facts. A deployment regression, database timeouts, provider failures causing checkout errors, and a currently expired credential were hypotheses. Treating the deployment as related to the incident or assuming checkout depends on particular services required verification. Claims that failures definitely began before or immediately after deployment, that credential checks had occurred, or that deployment logs showed no problem were unsupported.

My most important learning was that a language model can organise evidence, generate competing hypotheses, and suggest reversible checks, but it cannot confirm a root cause from an incomplete incident brief. Confidence, detail, structure, low variability, and repetition are not substitutes for logs, traces, a confirmed timeline, and human review.
